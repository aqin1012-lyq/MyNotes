## 为什么要学

前面四课你学的是一个个具体招式：注入（[[ai-prompt-injection]]）、RAG 越权（[[ai-rag]]）、过度代理（[[ai-agent]]）。这一课要做的是把这些零散招式**放进体系**——就像你当年把 SQLi、XSS、越权、SSRF 收进 OWASP Top 10 与安全开发流程一样。没有框架，你能修好一个漏洞；有了框架，你才能回答老板那句话：“我们的 AI 应用上线前，安全上到底要检查哪些项、由谁负责、怎么持续管理？”

这一课介绍四个互补的体系：**MITRE ATLAS**（攻击知识库，“别人会怎么打”）、**NIST AI RMF**（风险管理框架，“我们怎么治理”）、**NIST AI 100-2**（对抗机器学习的分类，“攻击有哪几大类”）、**Google SAIF**（一套面向工程落地的安全 AI 框架）。再加上你已经在用的 **OWASP Top 10 for LLM Applications 2025**，它们从不同角度覆盖同一片战场：ATLAS 偏攻击战术、OWASP 偏具体风险清单、NIST RMF 偏组织流程、NIST 100-2 偏学术分类、SAIF 偏工程实践。

对你这个从 Java 后端转安全的人，价值很实在：治理框架就是“上线前的 checklist + 上线后的运营机制”，落地时几乎都变成你熟悉的东西——评审门禁、依赖治理、权限矩阵、日志告警、应急响应。本课不追求背全所有条目，而是**能把框架当工具用**：知道遇到问题去查哪个、能给公司拟一份 AI 应用安全评审清单、能用工具给自己的 Agent Demo 做一次评估并写成报告。

:::warn 关于准确性
本课只描述这些框架的**结构与用途**，不列举具体的 MITRE ATLAS 技术编号、案例编号或真实事件——这些会随版本更新，且容易记错。要引用具体技术 ID 或案例时，请直接查各框架官网（见本主题 resources），以官方最新内容为准。
:::

## 核心概念

### 1. MITRE ATLAS：针对 AI 系统的攻击战术与技术

如果你了解 **MITRE ATT&CK**（把网络攻击按“战术阶段 × 具体技术”组织成矩阵的知识库），那 **ATLAS（Adversarial Threat Landscape for Artificial-Intelligence Systems）** 就是它面向 AI/ML 系统的对应物。它同样用“战术（tactics，攻击者的目标阶段，如侦察、初始访问、执行、外泄、影响）× 技术（techniques，达成目标的具体手法）”的结构，来描述**针对 AI 系统**的攻击，并配有真实世界启发的案例研究。

它和你学过的攻击的关系：ATLAS 把“投毒训练/知识库数据”“逃逸（对抗样本）”“模型窃取/反演”“提示注入”“供应链”等手法归入相应战术阶段，让你能系统地问“攻击者在侦察阶段会做什么、在外泄阶段又会做什么”，而不是零散记招式。

怎么用（作为防御方）：**威胁建模时按战术阶段过一遍**——针对我的 RAG/Agent，攻击者如何侦察（枚举工具、探系统提示词）？如何获得初始访问（间接注入、投毒文档）？如何执行与提权（借工具越权）？如何外泄（外链、外发工具）？如何造成影响（散布错误信息、烧资源）？每一格对照 [[ai-prompt-injection]]/[[ai-rag]]/[[ai-agent]] 里的具体防御，就得到一张覆盖检查表。

> 记住上面的准确性提示：需要引用某个具体技术编号或案例时去 ATLAS 官网查，不要凭记忆写编号。

### 2. NIST AI RMF：Govern / Map / Measure / Manage

**NIST AI Risk Management Framework（AI RMF）** 是一个**自愿性、面向组织**的 AI 风险管理框架。它不是技术清单，而是回答“一个组织该如何系统地管理 AI 风险”，核心是四个相互关联的职能：

| 职能 | 一句话 | 落到 AI 安全上大致对应 |
|---|---|---|
| Govern（治理） | 建立贯穿全流程的治理文化、责任、政策 | 谁负责 AI 安全、有无政策与评审门禁、供应商/模型准入 |
| Map（映射） | 弄清上下文，识别风险 | 这个 AI 系统用在哪、数据从哪来、面临哪些威胁（可借 ATLAS/OWASP 列举） |
| Measure（度量） | 分析、评估、跟踪风险 | 红队测试、扫描、评测指标、留痕 |
| Manage（管理） | 按优先级处置、监控、响应 | 修复/缓解、上线监控、告警、应急与持续复评 |

四者不是一次性瀑布，而是持续循环：Govern 贯穿始终，Map/Measure/Manage 随系统演进反复进行。NIST 还配有 **AI RMF Playbook** 等配套材料给出可操作建议。

对你的用法：**把 RMF 当成组织层的骨架，把 OWASP LLM Top 10 当成 Measure/Map 阶段的具体检查项**。比如“Map”时用 OWASP 十条逐项识别本系统暴露了哪些风险，“Measure”时用红队和扫描验证，“Manage”时排期修复并接入监控，“Govern”确保这套流程有人负责、每次上线都走。

### 3. NIST AI 100-2：对抗机器学习分类（投毒、逃逸、隐私攻击）

**NIST AI 100-2（Adversarial Machine Learning: A Taxonomy and Terminology）** 是一份把“对抗机器学习”攻击与缓解**术语标准化、分类化**的报告。它帮助你用统一语言讨论攻击，而不至于各说各话。抓住几个大类的直觉即可（具体细分与术语以报告原文为准）：

- **投毒（Poisoning）**：在训练或数据供给阶段掺入恶意数据，改变模型行为。对 LLM 应用而言，最贴近你的是**知识库/检索数据投毒**（见 [[ai-rag]]、OWASP LLM04），比动模型权重更现实。
- **逃逸 / 规避（Evasion）**：在推理阶段构造输入让模型判断出错（图像领域的“对抗样本”是典型）。在 LLM 语境里，可类比精心构造的提示绕过防护。
- **隐私攻击（Privacy attacks）**：从模型或其输出中反推训练/上下文数据，如成员推断、模型反演、数据提取，以及 [[ai-rag]] 提到的 **Embedding 反演**（OWASP LLM08）。
- **（滥用类）**：利用生成式模型能力本身作恶，如大规模生成虚假/有害内容（与 LLM09 Misinformation 相关）。

报告同时给出各类攻击的缓解方向及其**局限**——很多缓解只是提高成本而非根治，这与你在 [[ai-prompt-injection]] 学到的“没有银弹”一致。用法：当你需要向团队精确描述“我们担心的是哪一类攻击”时，用它的术语，避免把“投毒”“逃逸”“反演”混为一谈。

### 4. LLM 红队测试与自动化扫描工具

框架告诉你“要 Measure”，红队和扫描就是**怎么 Measure**。

**红队测试（red teaming）**：由人（或人+工具）主动扮演攻击者，针对性地尝试注入、越权、数据外泄、越狱、资源耗尽等，看防御是否真的挡得住。它是发现“组合型”“业务逻辑型”问题的主力——这些恰恰是自动扫描器测不到的。做法：以 OWASP LLM Top 10 和 ATLAS 战术为清单，逐项设计用例，覆盖直接/间接注入、RAG 越权、Agent 高危工具滥用、SSRF 出口、消耗上限等，记录每个用例的输入、预期、实际、结论。

**自动化扫描**：用工具批量发送已知的注入/越狱/泄露探针，快速回归。**garak** 是一个开源的 LLM 漏洞扫描器（NVIDIA 维护），内置多种探针（probe），对目标模型/端点批量测试并给出哪些探针“命中”的报告。它适合做**基线扫描和持续回归**（每次上线前跑一遍），但要清楚它的定位：探针是**已知模式**，测的是模型/端点层面的通用弱点，**测不到你的业务权限、工具授权、RAG 越权**这些应用逻辑——那些仍要靠红队和你自己写的测试（[[ai-rag]]、[[ai-agent]] 里的 JUnit）。两者互补：扫描保证不回退，红队发现新问题，应用测试证明关键安全性质恒成立。

### 5. 核心问题：AI 应用上线前的安全评审清单

把上面的框架落成一张可执行的门禁清单。这就是核心课程问题“向公司介绍‘AI 应用上线前的安全评审清单’，你会列哪些项”的答案。按 OWASP LLM Top 10 组织，每项都对应前几课的具体做法（也就是 NIST RMF 的 Map→Measure→Manage 在一次上线里的浓缩）：

- [ ] 治理（Govern）：本次上线有明确的安全负责人；走了评审门禁；用到的模型/外部工具/依赖经过准入。
- [ ] LLM01 注入：不可信内容已标注隔离；已假设注入会成功，边界在模型之外；做过直接/间接注入红队。
- [ ] LLM02 敏感信息泄露：系统提示词不含秘密；输出审查；PII/密钥入库前脱敏。
- [ ] LLM03 供应链：模型来源与版本可信、锁定；外部工具/MCP 服务器可信且锁版本；工具描述当不可信文本审查。
- [ ] LLM04 数据/模型投毒：知识库入库有来源审批与清洗；保留出处、可下架某来源全部文档。
- [ ] LLM05 输出处理：模型输出按去向编码/校验（HTML 编码、Schema 校验、外链域名白名单）。
- [ ] LLM06 过度代理：工具最小集、默认只读、以当前用户最小权限运行、高危操作人工确认；有统一执行层。
- [ ] LLM07 系统提示词泄露：假设会泄露，据此不放任何秘密与硬边界在提示词里。
- [ ] LLM08 向量/嵌入弱点：检索带 ACL、多租户隔离；向量库按敏感数据库加固（内网、加密、审计）。
- [ ] LLM09 错误信息：回答带出处；对高风险领域限定“只依据检索资料回答”；必要处加免责。
- [ ] LLM10 无限消耗：限步数、单次 max tokens、每用户速率与预算，并告警。
- [ ] 网络出口：所有能对外发请求的工具按 SSRF 加固 + 容器 egress 策略。
- [ ] 度量（Measure）：跑过 garak 基线扫描 + 关键安全性质有自动化测试 + 一轮人工红队，均留痕。
- [ ] 管理（Manage）：全链路审计日志（防篡改、脱敏）、异常告警、应急响应预案、定期复评计划。

这张表可以直接放进项目⑤的验收，也可以作为你给公司做分享的骨架。

## 动手实践

练习：**用 garak 扫描你自己的 Agent Demo，并把发现写成一份评估报告**。

> 只能扫描你自己的环境或已获书面授权的目标。garak 会发送大量攻击性探针，务必只对本机 Demo 运行。

### 第 1 步：安装并查看探针

garak 是 Python 工具，用 pip 安装即可（Python 版本要求以其官方 README 为准）：

```bash
python -m pip install garak
python -m garak --list_probes      # 列出内置探针（注入、越狱、泄露等）
```

预期：终端打印出一长串探针名称，按类别分组。怎么读：每个探针对应一类已知攻击模式，扫描时会挑选/指定这些探针对目标发起测试。

### 第 2 步：对目标运行扫描

garak 支持多种目标类型（generator），最简单是扫一个 OpenAI 兼容端点或本地模型；如果你的 Agent Demo 暴露了一个聊天 HTTP 接口，可用其 REST 类型的 generator 指向它（具体参数以官方文档为准，不同版本略有差异）。示意：

```bash
python -m garak --model_type rest --generator_option_file my_agent.json \
                --probes promptinject,leakreplay
```

预期：终端逐个探针跑，输出每个探针的通过/失败比例，并在结束时给出报告文件路径（garak 会生成一份运行报告，含每条探测的命中情况）。

```
probe: promptinject   ...  fail rate 22%
probe: leakreplay     ...  fail rate  5%
report written to  garak.<timestamp>.report.jsonl
```

怎么读：`fail rate` 是“探针成功攻破的比例”，越低越好。注意这是**模型/端点层**的结果，不代表你的应用整体安全——它测不到你的工具授权和 RAG 越权。

### 第 3 步：把发现写成评估报告

报告结构建议（就是把 NIST RMF 的 Measure→Manage 写下来）：

- 范围与方法：扫了哪个目标、garak 版本与探针集、还做了哪些人工红队用例、什么没覆盖（如业务权限）。
- 发现清单：每条一行——探针/用例、命中说明、映射到 OWASP LLM 哪一项与 ATLAS 哪个战术阶段、严重级、复现步骤。
- 处置建议：对应前几课的防御（隔离/权限/确认/输出校验/限额…），给出优先级与负责人。
- 残余风险与复评计划：哪些只能缓解不能根治、下次复评时间。

一份最小样例发现：

```
[发现1] promptinject 探针命中，fail rate 22%（OWASP LLM01 / ATLAS: 初始访问-执行阶段）
  说明: 模型端点对多类注入模式抵抗力有限。
  影响: 结合工具即可越权/外泄; 单独看仅影响输出可信度。
  处置: 已在执行层做权限隔离+人工确认(见 ai-agent), 属可接受残余; 增加输出审查与告警。 优先级中。
[发现2] 自写红队用例: 让 Agent fetch 169.254.169.254 -> 已被 SSRF 防护拦截(通过)。
```

怎么读：把自动扫描结果和自写红队/应用测试结果**放在同一张表里**，才是完整评估——garak 说明模型端点的通用弱点，你的 JUnit 与红队用例证明应用层边界成立。这份报告就是项目⑤“garak / 红队测试报告”里程碑。

## 攻击者视角

治理框架本身也是攻击者的“参考书”：ATLAS 就是从攻击方视角组织的，攻击者会照着战术阶段系统推进——侦察（枚举工具、探系统提示词）、初始访问（间接注入、投毒文档）、执行与提权（借工具越权）、外泄（外链/外发工具）、影响（错误信息、烧资源）。他们也知道自动扫描器的探针库长什么样，于是**专门构造扫描器测不到的业务逻辑攻击**（RAG 越权、工具链组合利用）——这正是为什么只靠 garak 远远不够，必须配人工红队。对防御方的启示：用同一套框架做威胁建模，才能想在攻击者前面。

## 防御与最佳实践

- **用框架而非零散招式**：ATLAS 做威胁建模、OWASP LLM Top 10 做风险清单、NIST RMF 做组织流程、NIST 100-2 统一术语、SAIF 指导工程落地。
- **把 RMF 落成上线门禁**：Govern（谁负责、准入）→ Map（用 OWASP 逐项识别）→ Measure（扫描+红队+应用测试并留痕）→ Manage（修复、监控、告警、复评），持续循环。
- **三层度量互补**：garak 等自动扫描保回归、人工红队找新问题、自写 JUnit 证明关键安全性质（权限过滤、工具授权、SSRF 防护）恒成立。
- **只对自己/授权目标测试**，扫描探针有攻击性。
- **引用具体编号去官网查**：ATLAS 技术 ID、NIST 术语、案例都随版本更新，别凭记忆写。
- **治理产物要落地**：评审清单、威胁模型、评估报告、审计与告警、应急预案，都要有人维护、定期复评。

## 常见误区

- **“上了框架就安全了”**：框架是流程和清单，真正的安全来自把每一项落成代码与运营；框架帮你不遗漏，不替你修漏洞。
- **“garak 跑绿了就没问题”**：扫描只覆盖模型/端点层的已知模式，测不到业务权限、工具授权、RAG 越权，必须配红队和应用测试。
- **“NIST AI RMF 是技术清单”**：它是组织层的风险管理框架（Govern/Map/Measure/Manage），要和 OWASP/ATLAS 这类具体清单配合。
- **“ATLAS 和 ATT&CK 没关系 / 可以互换”**：ATLAS 借用 ATT&CK 的战术×技术结构，但专门面向 AI 系统，二者针对的对象不同。
- **“把投毒、逃逸、反演混着说”**：用 NIST AI 100-2 的术语区分，沟通才精确。
- **“记住几个 ATLAS 技术编号显得专业”**：编号会变、易记错，需要时查官网，会用结构比背编号重要。

## 自测

:::details 1. MITRE ATLAS 是什么？和 MITRE ATT&CK 什么关系？防御方怎么用它？
ATLAS 是面向 AI/ML 系统的对抗威胁知识库，借用 ATT&CK 的“战术×技术”结构但针对 AI。防御方用它做威胁建模：按侦察→初始访问→执行/提权→外泄→影响等战术阶段，逐一问攻击者会怎么做、我对应的防御是什么，形成覆盖检查表。需要具体技术编号时查官网，不要凭记忆写。
:::

:::details 2. NIST AI RMF 的四个职能是什么？它和 OWASP LLM Top 10 怎么配合？
Govern（治理/责任/政策，贯穿始终）、Map（识别上下文与风险）、Measure（评估/度量/跟踪）、Manage（处置/监控/响应），持续循环而非瀑布。配合方式：RMF 是组织层骨架，OWASP LLM Top 10 是 Map/Measure 阶段的具体风险清单与检查项——用十条识别风险、用红队和扫描度量、按优先级管理修复。
:::

:::details 3. NIST AI 100-2 把对抗机器学习攻击大致分成哪几类？对 LLM 应用最贴近的是哪类？
大致分投毒（训练/数据阶段掺恶意数据）、逃逸/规避（推理阶段构造输入致误判）、隐私攻击（成员推断、模型反演、数据提取），以及滥用生成能力作恶。对 LLM 应用最贴近的是数据/知识库投毒（LLM04）和隐私类的 Embedding 反演/数据外泄（LLM08/LLM02）。具体细分以报告原文为准。
:::

:::details 4. 红队测试和 garak 这类自动扫描各自的定位与局限？为什么两者都要？
自动扫描（garak）用已知探针批量测模型/端点层的通用弱点，适合基线与回归，但测不到业务权限、工具授权、RAG 越权等应用逻辑。红队由人扮攻击者，擅长发现组合型/业务逻辑型问题，但难以规模化回归。两者加上自写的应用安全测试（JUnit 证明关键性质恒成立）三层互补，才算完整度量。
:::

:::details 5. 给 AI 应用上线前的安全评审清单，你至少会列哪些方向？
按 OWASP LLM Top 10 组织：注入隔离与红队(01)、敏感信息不入提示词与脱敏(02)、供应链模型/工具锁版本(03)、知识库投毒治理(04)、输出按去向校验(05)、工具最小权限+人工确认(06)、系统提示词假设泄露(07)、检索带 ACL 与向量库加固(08)、错误信息带出处(09)、消耗上限(10)，再加网络出口 SSRF 加固、度量(扫描+红队+测试留痕)、管理(审计告警+应急+复评)与治理(负责人+准入门禁)。
:::

:::details 6. 为什么说“框架不替你修漏洞”？它到底解决什么问题？
框架提供的是共同语言、威胁清单和管理流程，作用是让你系统化、不遗漏、可沟通、可持续，并明确责任与门禁。但每一项风险最终要靠具体的代码与运营手段去缓解（权限、确认、输出校验、限额、审计…）。把框架当成 checklist 和骨架，把前几课的做法当成血肉，二者结合才有效。
:::

:::details 7. 为什么不建议在报告或分享里凭记忆写 ATLAS 技术编号、具体案例或 NIST 条款号？
因为这些内容会随框架版本更新，且极易记错，写错反而损害可信度与准确性。正确做法是描述结构与用途，需要引用具体编号/案例/条款时现查官方最新来源并注明版本。
:::

## 一句话总结

治理框架是把 AI 安全从“会修单个漏洞”升级到“能管住整个系统”的工具箱：**ATLAS 帮你想清攻击、OWASP LLM Top 10 列全风险、NIST AI RMF 用 Govern/Map/Measure/Manage 把它变成上线门禁与持续运营、NIST 100-2 统一术语、garak+红队+应用测试三层度量**——框架保证你不遗漏，前几课的代码与运营手段负责真正把风险摁住。
