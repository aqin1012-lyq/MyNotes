## 为什么要学

前三课你已经能在技术上把一个 IoT 平台做安全：[[iot-mqtt]] 看清攻击面，[[iot-identity]] 做一机一证，[[iot-acl]] 做主题授权。但在企业里，安全工作最终要回答另一类问题：“我们的产品符合哪些标准？”“这辆车能不能通过型式认证？”“客户审计时拿什么证明我们做过威胁分析？”这些问题靠标准和法规来回答。

对你来说，这一课是把**汽车/IoT 项目经历升级为可以对外讲的专业方向**的关键。面试车企、Tier 1 供应商或 IoT 平台公司的安全岗位时，能说清 ISO/SAE 21434 的 TARA 流程、UN R155 对车企意味着什么、ETSI EN 303 645 有哪些基线要求，再结合“我亲手在 EMQX 上做过一机一证和主题 ACL”，这是纯 Web 安全背景的人很难提供的组合。

学完你应该能：说出 OWASP IoT Top 10 的十项并对应到前几课的内容；讲清 EN 303 645 的核心基线；理解 21434 的整体结构和 TARA 的步骤；区分 R155（网络安全管理体系）与 R156（软件升级管理体系）；讲清 OTA 签名与防回滚；并为项目③做一份简化版 TARA。

:::warn 关于准确性
标准文本本身大多需要购买或注册下载，而且会修订。本课只讲结构和核心要求，**不引用具体条款编号**；需要写进正式文档或对外材料时，请以你拿到的标准原文（注意版本号）为准。课程资源里的链接是官方入口。
:::

## 核心概念

先看全景，这几份文件定位不同，不要混为一谈：

| 名称 | 性质 | 适用对象 | 一句话 |
|---|---|---|---|
| OWASP IoT Top 10 | 社区风险清单（非强制） | 所有 IoT 产品 | 最常见的十类 IoT 安全问题 |
| ETSI EN 303 645 | 欧洲标准（自愿采用，但被多国法规/认证引用） | 消费级 IoT | 消费级 IoT 的安全基线 |
| NIST IR 8259 系列 | 美国 NIST 的指导文件 | IoT 设备制造商 | 制造商应做的活动与设备应具备的能力 |
| ISO/SAE 21434 | 国际标准（工程方法） | 汽车及零部件 | 汽车网络安全工程怎么做，含 TARA |
| UN R155 / R156 | 联合国法规（在采用它的国家/地区强制） | 车企（整车型式认证） | 必须有网络安全管理体系 / 软件升级管理体系 |

### 1. OWASP IoT Top 10

OWASP IoT 项目发布的 Top 10（目前广泛引用的是 2018 版）：

| 编号 | 风险 | 在前几课中的对应 |
|---|---|---|
| I1 | 弱口令、可猜测或硬编码的密码 | EMQX Dashboard 默认口令、一型一密硬编码在固件 |
| I2 | 不安全的网络服务 | 公网暴露的 1883、18083、集群端口 |
| I3 | 不安全的生态接口（Web、API、云、移动端） | 平台指令 API 的 IDOR、回调接口暴露 |
| I4 | 缺乏安全的更新机制 | OTA 不验签、无防回滚（本课第 6 节） |
| I5 | 使用不安全或过时的组件 | 固件里的老旧 OpenSSL、Linux 内核、第三方库 |
| I6 | 隐私保护不足 | 订阅 `#` 泄露位置、轨迹等个人数据 |
| I7 | 不安全的数据传输与存储 | 明文 1883、私钥明文存 Flash |
| I8 | 缺乏设备管理 | 无法吊销、无法下线、无资产清单 |
| I9 | 不安全的默认设置 | 默认允许匿名、`no_match = allow` |
| I10 | 缺乏物理加固 | 调试串口/JTAG 未关，拆机即可读固件 |

用法：它适合作为**检查清单和沟通语言**，不是认证标准。另外 OWASP 还有更细的 IoT 安全验证标准 ISVS，可用来写测试用例。

### 2. ETSI EN 303 645：消费级 IoT 安全基线

EN 303 645 面向消费级 IoT 产品（智能音箱、摄像头、门锁、家电、可穿戴设备等），由若干条“规定（provision）”组成，分为强制性（mandatory）和建议性（recommended）两类，并分成 13 个网络安全类别外加一组数据保护要求。13 个类别是：

- 不使用通用默认密码
- 实施管理漏洞报告的方法（漏洞披露政策）
- 保持软件更新
- 安全存储敏感的安全参数
- 安全通信
- 最小化暴露的攻击面
- 确保软件完整性
- 确保个人数据安全
- 使系统对中断具有韧性
- 检查系统遥测数据
- 让用户能方便地删除用户数据
- 让设备的安装和维护变得简单
- 校验输入数据

课程要点里强调的三条是整个标准最核心、也最常被法规引用的：**禁止通用默认密码**（每台设备唯一密码或由用户首次设置）、**公开漏洞披露渠道**（外部研究者能报告漏洞、厂商会跟进处理）、**安全更新**（提供更新并明确告知支持周期）。英国等地的消费级 IoT 法规就借鉴了这几条。

### 3. NIST IR 8259 系列（补充）

课程资源里列了 NIST IR 8259。需要先澄清一个容易混的点：这是一个**系列**。IR 8259 本身讲的是 IoT 设备制造商应开展的基础网络安全活动（在设计开发前后要做什么），而资源标题里的“设备网络安全能力核心基线”是同系列的 **IR 8259A**，另外 **IR 8259B** 讲非技术性支持能力。

- **IR 8259A 的技术能力基线**（设备本身应具备）：设备标识、设备配置、数据保护、对接口的逻辑访问控制、软件更新、网络安全状态感知。
- **IR 8259B 的非技术能力**（制造商应提供）：文档、接收信息与询问、信息发布（例如通知漏洞和更新）、教育与意识。

把它和前几课对照：一机一证对应“设备标识”；主题 ACL 和关闭多余端口对应“逻辑访问”；私钥进安全芯片对应“数据保护”；OTA 对应“软件更新”；授权拒绝日志和异常检测对应“状态感知”。

### 4. ISO/SAE 21434 汽车网络安全工程与 TARA

ISO/SAE 21434（2021 年发布）规定的是汽车电子电气系统在**整个生命周期**里的网络安全工程要求，它不规定用哪种加密算法，而是规定“流程上必须做什么、要留下什么工作产物”。整体结构可以这样理解：

```
Organizational cybersecurity management       组织层：方针、文化、能力、审核
Project-dependent cybersecurity management    项目层：计划、裁剪、案例、评估
Distributed activities                        供应链：与供应商/客户的职责分工
Continual activities                          持续：监控、事件评估、漏洞分析与管理
Concept  -> item definition, goals            概念阶段：定义对象、网络安全目标
Development -> design, verification           开发阶段：设计、集成与验证
Validation                                    整车层确认
Production / Operations & Maintenance         生产、运行维护（事件响应、更新）
End of support / Decommissioning              停止支持与报废
TARA methods                                  贯穿各阶段的威胁分析与风险评估方法
```

**TARA（Threat Analysis and Risk Assessment）** 是其中最核心、也最常被问到的方法，步骤是：

1. **资产识别**：找出有网络安全属性（机密性、完整性、可用性等）的资产，比如“车门解锁指令”“设备私钥”“用户位置数据”，并识别**损害场景**（资产属性被破坏后造成的后果）。
2. **威胁场景识别**：谁、通过什么方式破坏了哪个资产的哪个属性，比如“攻击者伪造下行解锁指令，破坏指令完整性”。
3. **影响评级**：从**安全（Safety）、财务（Financial）、运营（Operational）、隐私（Privacy）**四个维度评估损害场景的严重程度，等级为严重、重大、中等、可忽略。
4. **攻击路径分析**：威胁场景可以通过哪些具体路径实现（远程、近场、物理接触）。
5. **攻击可行性评级**：标准给出了几种方法，常见的是基于“攻击潜力”的方法，考虑所需时间、专业能力、对目标的了解程度、机会窗口、所需设备等因素；也可以基于 CVSS 或基于攻击向量来评。
6. **风险值确定**：由影响等级和攻击可行性共同确定风险值。
7. **风险处置决策**：对每个风险选择**规避、降低、转移（分担）或接受（保留）**，降低的话要落到网络安全目标和需求上。

在工作中你最可能接触的形式是一张大表：一行一个威胁场景，列上是资产、损害场景、影响评级、攻击路径、可行性、风险值、处置决策、对应的安全需求。后面的“动手实践”里你会自己填一张。

### 5. UN R155 / R156：车辆网络安全与软件升级法规

UN R155 和 R156 是联合国欧洲经济委员会（UNECE）WP.29 框架下的法规，在采用它们的缔约方（包括欧盟、日本、韩国等）作为**整车型式认证**的条件，也就是说：不满足就不能上市销售。欧盟已对新车型和新生产车辆分阶段强制实施。中国也发布了对应的汽车整车信息安全和软件升级方面的强制性国家标准，思路与 R155/R156 接近，做国内项目时请查阅最新发布的国标原文。

| | UN R155 | UN R156 |
|---|---|---|
| 主题 | 网络安全 | 软件升级 |
| 对组织的要求 | 建立并获得认证的 **CSMS**（网络安全管理体系） | 建立并获得认证的 **SUMS**（软件升级管理体系） |
| 对车型的要求 | 该车型做过风险评估、实施了相应缓解措施，覆盖供应链，并能持续监控与响应 | 升级过程安全可靠，能证明车辆软件版本与认证状态的对应关系 |
| 典型关注点 | 法规附件中列出了一份威胁与缓解措施清单（后台服务器、通信通道、更新过程、人为行为、外部接口、数据等），车企需说明如何覆盖 | 升级包的真实性和完整性保护、升级前后的安全状态、告知用户、失败处理；用 **RXSWIN**（软件识别号）标识与型式认证相关的软件版本 |

两者与 21434 的关系：R155 规定“你必须有一个合格的网络安全管理体系”，而 ISO/SAE 21434 通常被用来作为**如何建立这个体系**的工程方法依据；R156 常与 ISO 24089（道路车辆软件升级工程）配套使用。对后端工程师来说，TSP/车联网平台、OTA 平台、远程控车 API 都在 R155 所说的“后台服务器”和“通信通道”范围内，你前几课做的每一件事都能写进 CSMS 的证据里。

### 6. OTA 升级的签名与回滚保护

OTA 是 IoT 和车联网攻击面里最“值钱”的一环：谁能推固件，谁就控制了全部设备。

```
build server --> sign(firmware, K_priv) in HSM   私钥只在 HSM 中
     |
     v
OTA server: manifest {version, hash, target, expiry} + signature
     |
     v  (HTTPS / MQTT down + download URL)
device:
  1. verify signature with K_pub (in ROM / secure storage)   验签，公钥不可被替换
  2. check hash of downloaded image                          完整性
  3. check version > stored min version                      防回滚
  4. write to inactive slot (A/B), reboot, self-test         失败自动回退到旧槽
  5. update secure monotonic counter                         记录新的最低版本
```

- **签名**：固件和清单（manifest）用平台私钥签名，私钥放 HSM 或云 KMS；设备内置公钥，并保证公钥本身不能被替换（放 ROM、安全芯片或受安全启动保护的区域）。只靠 HTTPS 下载不够，因为 OTA 服务器被入侵时，攻击者可以推送任意文件。
- **防回滚**：攻击者把设备“降级”到一个有已知漏洞的旧版本，签名是真的，却能重新打开漏洞。防法是设备记录一个**只增不减的最低允许版本**（最好存在安全芯片的单调计数器中），低于它的包一律拒绝。
- **A/B 分区**：保证升级失败时能回到“当前可用版本”——这里的“回滚”是可靠性机制，与上面禁止的“降级攻击”不同，别混淆。
- **业界框架**：汽车领域有专门针对 OTA 的 Uptane 框架，它基于通用软件更新框架 TUF，通过多角色签名防止单个服务器被攻破后推送恶意更新。

## 动手实践

### 练习：对自己的 IoT Demo 做一次简化版 TARA

对象（item）就是项目③：EMQX + Spring Boot 平台 + Paho 设备模拟器 + 指令下发 API。建议在项目里建一个 `docs/tara.md`，按下面四步做。

**第 1 步：画出对象边界和数据流**

```
[App/Ops] --HTTPS--> [Platform API] --MQTT(8883, mTLS)--> [EMQX] --> [Device]
                          |                                   |
                       [MySQL/Redis]                     [Dashboard 18083]
trust boundaries: internet | platform network | device (physical access possible)
```

**第 2 步：列资产与损害场景**

| 资产 | 属性 | 损害场景 |
|---|---|---|
| 下行指令（解锁/启动） | 完整性、真实性 | 车辆被非车主解锁 |
| 设备私钥 | 机密性 | 设备身份被克隆 |
| 上行数据（位置、车速） | 机密性 | 用户轨迹泄露 |
| EMQX 管理面 | 完整性、可用性 | 规则/授权被篡改、全网掉线 |
| OTA 固件 | 完整性 | 全部设备被植入恶意固件 |

**第 3 步：威胁场景、影响、可行性、风险**

简化起见，影响和可行性各用“高/中/低”，风险取两者组合：

| # | 威胁场景 | 影响（S/F/O/P） | 攻击路径 | 可行性 | 风险 | 处置 | 安全需求 |
|---|---|---|---|---|---|---|---|
| T1 | 合法设备订阅 `#` 获取所有用户位置 | P 高 | 远程，有一台设备即可 | 高 | 高 | 降低 | 主题 ACL 默认拒绝、禁止通配符 |
| T2 | 拆机提取一型一密密钥冒充全型号 | S/F 高 | 物理接触一台设备 | 中 | 高 | 降低 | 一机一证、私钥入安全芯片 |
| T3 | ClientID 抢占接管下行指令 | S 高 | 远程，需任一合法证书 | 中 | 高 | 降低 | ClientID 必须等于证书 CN |
| T4 | 重放抓到的解锁指令 | S 高 | 需能向下行主题发布 | 低（已有 ACL） | 中 | 降低 | 指令签名 + nonce + 过期 |
| T5 | 保留消息投毒下行主题 | S 高 | 需下行发布权限 | 低 | 中 | 降低 | 下行不用 retain、设备验签 |
| T6 | Dashboard 默认口令被利用 | O 高 | 远程，18083 可达 | 视暴露面 | 高 | 降低 | 改口令、只开内网 |
| T7 | 用户通过平台 API 改 VIN 解锁他人车辆 | S 高 | 远程，普通用户账号 | 高 | 高 | 降低 | API 对象级授权 + 审计 |
| T8 | 降级到有漏洞的旧固件 | S 中 | 需能推送旧的已签名包 | 低 | 中 | 降低 | 最低版本单调计数器 |

**第 4 步：追踪处置**

每个“降低”的风险，写出它落在哪个代码或配置里（比如 T1 → `DevicePolicy.authorize` + `DevicePolicyTests.wildcardsAreDenied`），并注明剩余风险。“接受”的风险要写理由和签字人（在个人项目里就是你自己）。

读法：做完你会发现，前三课的每个功能都能在表里找到“它为什么存在”——这就是 TARA 的价值：**从威胁推导出需求，而不是先堆功能**。真实 21434 项目中的影响评级和可行性评级要按标准给出的等级与因素打分，本练习只取其骨架。

### 思考题：按 EN 303 645 检查过去的项目（只写笔记）

回忆你做过的汽车/IoT 项目，逐项自问并写进个人笔记（**不要写公司敏感信息**）：设备或管理后台是否有全体通用的默认密码？有没有对外公开的漏洞报告渠道？是否承诺过软件更新支持周期？设备密钥是否明文存储？通信是否全程加密？调试口和不用的端口是否关闭？固件是否有签名校验和防回滚？遥测里是否能发现异常？用户能否删除自己的数据？常见的答案是“一型一密”“MQTT 1883 明文内网”“OTA 只校验 MD5”“没有漏洞披露渠道”，这些都直接对应不合规项。

## 攻击者视角

> 本课涉及的攻击只可用于你自己的环境或已获授权的目标。

攻击者不读标准，但标准里的每一条都是对某类真实攻击的总结。从攻击者的角度，可以把标准读成一份“常见突破口清单”：

- **通用默认密码** → 批量扫描公网设备和管理后台（对应 OWASP 的 I1，以及 EN 303 645 的“不使用通用默认密码”）。
- **没有漏洞披露渠道** → 研究者发现问题后无处报告，漏洞更可能在地下流通或被直接公开。
- **更新不验签或可降级** → 控制 OTA 服务器或中间人即可推送恶意固件；或把设备降级到有已知漏洞的版本。
- **敏感参数不安全存储** → 拆机读 Flash 提取密钥（一型一密即全型号沦陷）。
- **不做遥测检查** → 攻击者可长期潜伏，枚举、越权尝试没有人看见。
- **后台服务器和通信通道** → R155 把它们列为车辆威胁的一部分：打穿 TSP 平台或远程控车 API，远比逐辆车攻击效率高。

另一个现实角度：合规文档本身也会被“表演”——TARA 写得漂亮，但代码里没有对应的控制措施。所以安全评估时要**用测试去验证 TARA 里声称的每一项缓解措施**，就像你在 [[iot-acl]] 里用测试证明“设备 A 读不到设备 B”。

## 防御与最佳实践

- **把标准当需求来源**：以 EN 303 645 / NIST IR 8259A 做设备基线，以 OWASP IoT Top 10 做检查清单，以 21434 的 TARA 做风险驱动，以 R155/R156 做车企合规目标。
- **需求可追溯**：每条安全需求能追到 TARA 中的威胁，能追到代码/配置，能追到测试用例。这正是 21434 所要求的工作产物思路，也是审计时最有说服力的证据。
- **持续活动不能缺**：漏洞监控（关注所用组件的漏洞通报）、事件响应、定期复审 TARA；R155 要求的是持续的管理体系，而不是一次性报告。
- **OTA 做全**：签名（私钥在 HSM）、清单含版本/目标/过期时间、设备侧验签、单调计数器防降级、A/B 分区保可用，并对 OTA 平台本身做最小权限和审计。
- **漏洞披露**：公开一个安全联系方式和处理流程，给出响应时限，内部有分级处理机制。
- **供应链**：21434 强调分布式活动，要和供应商明确谁负责哪部分的网络安全；在 Java 侧就是依赖管理、SBOM、组件漏洞扫描。

## 常见误区

- **“OWASP IoT Top 10 是一个认证标准。”** 它是风险清单和沟通工具，不能“通过认证”。
- **“EN 303 645 是欧洲法律。”** 它本身是标准，是否强制取决于引用它的法规或认证方案。
- **“21434 规定了用什么加密算法。”** 它规定的是流程和工作产物，具体技术措施由 TARA 推导。
- **“R155 是给零部件供应商的认证。”** R155/R156 是整车型式认证的条件，对象是车企（车辆制造商）；供应商通过车企的供应链要求间接受约束。
- **“TARA 做一次就完了。”** 新漏洞、新功能、新攻击手法出现时都要复审，这属于持续活动。
- **“OTA 用 HTTPS 下载就安全了。”** HTTPS 只保护传输，不能防 OTA 服务器被攻破后推送恶意包，也不能防降级。必须有端到端签名和防回滚。
- **“A/B 回滚和防回滚矛盾。”** 前者是升级失败时回到当前可用版本，后者是禁止降级到被淘汰的旧版本，两者同时存在。

## 自测

:::details 1. OWASP IoT Top 10 有哪些？挑三项对应到你的 EMQX 项目。
弱/硬编码密码、不安全的网络服务、不安全的生态接口、缺乏安全更新机制、使用不安全或过时组件、隐私保护不足、不安全的数据传输与存储、缺乏设备管理、不安全的默认设置、缺乏物理加固。对应举例：Dashboard 默认口令与一型一密（弱/硬编码密码）；公网暴露 1883/18083（不安全网络服务）；EMQX 默认允许匿名、`no_match` 放行（不安全默认设置）。
:::

:::details 2. ETSI EN 303 645 最核心的三条基线是什么？
不使用通用默认密码（每台唯一或用户首次设置）；实施漏洞报告管理（公开披露渠道并跟进处理）；保持软件更新（提供安全更新并明确支持周期）。完整标准共 13 个网络安全类别，外加数据保护要求，规定分强制和建议两类。
:::

:::details 3. TARA 的主要步骤有哪些？影响评级从哪几个维度看？
资产识别与损害场景 → 威胁场景识别 → 影响评级 → 攻击路径分析 → 攻击可行性评级 → 风险值确定 → 风险处置决策（规避、降低、转移、接受）。影响从安全、财务、运营、隐私（S/F/O/P）四个维度评估，等级为严重、重大、中等、可忽略。
:::

:::details 4. UN R155 和 R156 分别要求什么？和 ISO/SAE 21434 什么关系？
R155 要求车企具备经认证的网络安全管理体系（CSMS），并证明车型做了风险评估和缓解；R156 要求经认证的软件升级管理体系（SUMS），保证升级安全并用 RXSWIN 标识相关软件版本。它们是采用国家/地区的整车型式认证条件。ISO/SAE 21434 是工程标准，常被用作建立 CSMS 的方法依据。
:::

:::details 5. NIST IR 8259 和 8259A 有什么区别？8259A 列了哪些设备能力？
IR 8259 讲制造商应开展的基础网络安全活动；IR 8259A 是设备网络安全能力核心基线，包括设备标识、设备配置、数据保护、接口逻辑访问、软件更新、网络安全状态感知；IR 8259B 讲文档、信息接收、信息发布、教育意识等非技术能力。
:::

:::details 6. OTA 为什么只用 HTTPS 不够？防回滚怎么做？
HTTPS 只保护传输，OTA 服务器或构建链被攻破时仍可推送恶意固件；需要用 HSM 中的私钥对固件与清单签名，设备用受保护的公钥验签。防回滚是设备保存只增不减的最低允许版本（最好在安全芯片的单调计数器中），拒绝低于它的包，防止降级到有已知漏洞的合法旧版本。A/B 分区的“失败回退”是另一回事。
:::

:::details 7. 按 EN 303 645 检查过去的项目，常见不合规项有哪些？
典型的有：一型一密或设备/后台使用通用默认密码；没有公开的漏洞报告渠道；没有承诺的更新支持周期；密钥明文存储；内网 MQTT 使用明文 1883；调试口未关闭；OTA 只做 MD5 校验而无签名、无防回滚；没有遥测异常检测；用户无法删除个人数据。具体写进个人笔记，不写公司敏感信息。
:::

## 一句话总结

标准和法规是把“安全做得好”翻译成行业通用语言的工具：OWASP IoT Top 10 做清单，EN 303 645 与 NIST IR 8259 定设备基线，ISO/SAE 21434 用 TARA 从威胁推导需求，R155/R156 把这一切变成车企上市的门槛——而你在项目③里写的每一行代码，都应该能在 TARA 表里找到它存在的理由。
